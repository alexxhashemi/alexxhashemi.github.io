Shiraz, Autonomous Multi-Agent System

A self-hosted multi-agent system running on Hermes Agent (Nous Research). Seven profiles in total: one orchestrator and six headless specialists. I only ever message one of them.

Shiraz is not a layer above Hermes. Shiraz is a Hermes profile, running on the same engine as every specialist below it. What makes it the orchestrator is not privileged infrastructure: it holds the schedule, the routing rules, and the only messaging gateway in the system.

A day in the system

What the system produces

Pipeline 01 daily

AI, Tech and Space News

News Agent archives stories through the day. X Post Agent searches and publishes to X three times daily, independently. Video Producer reads the archive at 16:30, picks its own stories, and renders a finished multi-scene video to YouTube.

How it works archive, posting, video render, cleanup
01

News Agent

Six staggered passes a day scan AI, ML, tech and space news, appending clean summaries to news_archive. A text-similarity check drops near-duplicate stories before they reach production. This archive feeds the video pipeline only.

02

X Post Agent

Deliberately self-contained: it searches for post-worthy items and publishes in the same run, and never reads the archive. Three times daily, through Buffer's API. Posting times come from published engagement research rather than a guess.

03

Video Producer

Reads the archive and selects several distinct stories itself, rather than being handed one topic. Writes a script segment per story, generates a voiceover per segment via Grok TTS with character-level timestamps, fetches a separate matched stock clip per segment from Pexels, cuts scene to scene, renders locally with HyperFrames (HTML/CSS/GSAP compiled to MP4 via headless Chrome and FFmpeg), then uploads through the YouTube Data API v3.

04

Cleanup

A nightly deterministic script on fixed retention windows: one day for generated media, three for archive entries. Age-based deletion, no model calls, no judgement. That is why it is the one specialist here not called an agent.

The decision that shaped the build: the obvious approach is to call an AI video-generation API, which bills per second of rendered footage, roughly $2.40 per video in testing. Rendering locally brought the marginal cost down to cents, with voiceover the only remaining per-video API charge.

Details that came out of building it

  • Footage is matched per story rather than one clip stretched across the whole video.
  • Scene cuts are timed to character-level TTS timestamps rather than an equal split, so cuts land on the words being spoken.
  • Clips are tiled rather than looped, because deterministic renderers stall when asked to seek past the end of a source file.
Pipeline 02 weekly

Internals: a weekly study brief

Two agents in a strict chain every Sunday. Internals Writer (Claude Sonnet 5.5) researches four topics on how technical systems actually work and drafts a short brief on each; Internals Auditor (Grok 4.7) scores them against a rubric. The scores are advisory: they never auto-reject. The briefs come to me as private study notes, and I decide which ones are worth keeping.

How it works formats, the Sunday chain, two different gates

The four formats

01

Mechanics

How something actually works: an algorithm, data structure, or technique, at the mechanism level rather than tied to a product.

02

Anatomy

Dissecting a system into the jobs it must do, using specific products only as illustration.

03

Case File

A documented incident reconstructed: what happened, what it exposed, what stayed true afterwards. Drawn from a pre-vetted bank of real, sourced incidents, never invented live. If the bank runs dry the format is skipped for the week rather than filled with a fabricated case.

04

Concept + Critique

An idea explained on its own terms, then examined for where it breaks or gets asked to carry more than it can.

The Sunday chain

  • 09:00, Internals Writer (Claude Sonnet 5.5) finds material and drafts all four briefs, checking each against earlier weeks so it never repeats a topic.
  • 09:20, Internals Auditor (Grok 4.7) scores each brief on a rubric: non-obvious, mechanism depth, durability, accuracy, and for case files, sourcing.
  • Shiraz sends the four briefs plus their audit scores to Telegram.
  • I decide which to keep: the whole batch, a subset, or none.

Sourcing is enforced twice, and the two are not the same thing. The Auditor scores sourcing quality, but that score is advisory and blocks nothing. Separately, a check in code hard-blocks any case-file draft with no sources attached, before it ever reaches me. One is a judgement, the other is a gate. Keeping them distinct matters: an advisory score that silently becomes a blocker is a system whose behaviour you can no longer predict.

Pipeline 03 event-driven

Medical Appointment Automation

Bridges a locked, API-less hospital portal into an intelligent pipeline. Runs entirely outside Hermes in Make.com, and its only touchpoint with the agent system is the final Telegram step, which points at Shiraz's bot like everything else.

How it works the constraint, extraction, agent handoff

The problem: UHN's patient portal (Epic MyChart) exposes no public API for appointment data. No webhook, no calendar feed by default, no way to pull scheduled visits programmatically. The only reliable signal the system emits is a confirmation email from a specific sender every time an appointment is booked. That email is the only extraction point.

01

Gmail, watch emails (trigger)

Polls Gmail on a 24-hour interval, filtered to the UHN appointment sender. When a matching email arrives, it passes the full plain-text body downstream.

02

Text parser, match pattern

A single regex with named capture groups extracts every relevant field in one pass, outputting five clean variables: date, appointment_time, arrival_time, provider, and department. The bridge pattern handles the variable-length block between arrival time and the provider and department lines, which differs between appointment types, and the provider group is optional because not all confirmations include one.

03

Google Calendar, create event

Maps the parsed variables directly into a new calendar event. Date and time fields are mapped explicitly rather than using natural-language "quick add" mode, which would require passing a single string and risk a misparse. The event name is built from department so appointments are immediately identifiable.

04

Telegram, agent handoff

Fires a formatted message to Shiraz's bot carrying all five parsed fields. This is where the pipeline stops being a simple automation and becomes an agent handoff.

Why the Telegram step matters: Google Calendar receives the appointment as a dumb calendar block. Shiraz receives it as structured, reasoned input. Because it gets the raw fields rather than just a notification, it can do things a calendar event cannot: cross-reference the appointment against my existing schedule, calculate departure time based on hospital location, flag back-to-back appointments where one arrival time overlaps the end of another, or surface pre-appointment instructions buried in the email body. Make handles extraction and fan-out, Shiraz handles the intelligence layer, and each tool does what it is actually good at.

The only constraint is the 24-hour polling interval on the Gmail trigger, a Make free-tier limitation that drops to 15 minutes on a paid plan.

In progress

Voice interface

Talking to Shiraz locally

Everything above is driven by typing into a Telegram bot. The next extension is voice: speaking to the agent the way you would to a smart speaker, without sending any audio to Amazon or anyone else. Three local, open-source pieces chained together, none of which need a network connection to do their job.

How it works wake word, transcription, speech, and what stays on the machine

Voice is not a new agent, it is a new interface to the one that already exists. The wake word script does not know or care that its output is about to become spoken audio rather than a Telegram reply. From Shiraz's side a spoken question and a typed one look identical, which is why this adds a way in without adding an eighth profile to the system.

01

openWakeWord

Listens continuously for a wake phrase and does no real processing until it hears one. Everything downstream stays idle until this fires.

02

Whisper, via faster-whisper

Transcribes the spoken question to text on-device, once the wake word has triggered.

03

Piper

Turns Shiraz's text reply back into speech, also entirely locally.

What actually leaves the machine

  • No audio, at any stage. Listening, transcription and playback all happen on-device.
  • Only the question text, which reaches Shiraz's existing model backend exactly the way a Telegram message already does.

Where it stands

  • Proven piece by piece so far: Piper generating natural speech from text, and the microphone and wake-word detection picking up spoken audio in real time.
  • Still to do: wiring those pieces into one continuous loop, connecting that loop to Shiraz's backend, and training a custom "hey Shiraz" wake word to replace the stand-in phrase.

Design notes

Why six specialists instead of one agent the case for splitting, and what it cost

All of this ran as a single Hermes agent first, and it worked. The case for splitting was not that more agents are inherently better. It was three specific problems that only show up once several distinct jobs share one context.

Failure isolation

A misfire in one job used to risk the whole agent's context. One bad reasoning loop sat in the same session as the code publishing that day's video. Split apart, a stuck News Agent run has zero effect on whether Video Producer or X Post Agent complete theirs.

Cost matched to the actual job

One model for everything means every task pays for whatever the most demanding task needs. Split, each profile's model reflects what it actually does, down to Cleanup needing no model at all. That distinction was invisible inside one shared agent.

Memory that does not dilute

In one agent, everything it learns sits in the same memory: which news sources double-post, what the video voice sounds like, what makes a good Internals entry. Split, each profile's memory fills only with what is relevant to its one job, so News Agent gets sharper at source reliability without that being buried under video-pacing notes.

What splitting did not do: make any single profile smarter. Same model capability either way. The entire benefit is structural: smaller blast radius, spend that matches the task, memory that compounds toward the right thing. It also is not free. Six profiles is more surface to configure, monitor and maintain than one. The trade was worth making here because four genuinely distinct jobs had already accumulated on one profile, not because splitting is correct by default.

Migration notes how the cutover was sequenced, and what went wrong

Moving from one profile to seven could not be done in a single switch. The original single-profile Shiraz was still running every equivalent job on the same schedule, so starting a new profile before disabling the old job produces duplicate work: duplicate posts, duplicate renders, duplicate archive writes.

So cutover ran one profile at a time. Disable the old job and start the new gateway in the same sitting, then confirm that profile's first real unattended run before touching the next one. Slower than a big-bang switch, but each step is verifiable and reversible on its own.

What went wrong, and what it taught

  • News Agent's four search jobs ran in parallel with the original profile's equivalent jobs for several hours before the duplication was noticed and the old copies removed. The one-at-a-time discipline above is a direct response to that, not a precaution written in advance.

Self-hosted

Rakazo, an open-source alternative to Grok Bot

xAI's Grok Bot gives an agent its own browser and terminal on a cloud machine, at $200 a month standalone or bundled into a top-tier subscription. Rakazo is an open-source equivalent I run on my own hardware, alongside everything above. Each bot gets a disposable Linux container with a real browser, a terminal, a filesystem, and memory that survives between sessions. The framework itself is free, so the only cost is model tokens, and the provider is a dropdown rather than a dependency: it is pointed at Grok 4.3 today, and nothing breaks if that changes.

I keep it scoped to work that genuinely needs a browser session and has no clean API:

  • Checking portals that offer no notification of their own, on a schedule.
  • Filling forms on sites that expose no API.
  • Click-through and rendering checks on my own pages.
  • Reading sources that refuse headless requests but tolerate a real browser.

Anything reachable by an API or a plain script is handled elsewhere. This exists for the residue that is not. It listens on loopback only, has no messaging channel of its own, and holds no write access to anything that matters, so its output reaches me by file or by my going and looking. The honest trade is that you give up polish and somebody else's on-call rota, and get data locality and no vendor lock-in in exchange.
